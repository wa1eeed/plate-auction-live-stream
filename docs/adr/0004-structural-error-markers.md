# ADR-0004: علامات أخطاء بنيوية بدل `instanceof`

**الحالة**: مقبول · **الدافع**: عطل حقيقي في الإنتاج المحلي

## السياق

الأخطاء المعروفة (`ServiceError`, `TradeError`) تحمل `status` و`code` يحوّلهما
`handleError` إلى استجابة HTTP دقيقة.

الفحص الأول كان `error instanceof ServiceError`. وفشل.

السبب: `instanceof` يقارن سلسلة النماذج (prototype chain)، وهي تفشل عندما
تُحمَّل الوحدة نفسها أكثر من مرة — وهو ما يحدث فعلًا عبر حدود حزم Next
(خادم/عميل، حزم منفصلة، إعادة تحميل ساخن). النتيجة: خطأ صحيح تمامًا لا
يُتعرَّف عليه، فيسقط إلى الفرع العام ويضيع `status` و`code`. عمليًا: خطأ عمل
واضح يعود `400 ERROR` بدل `409 AMOUNT_TOO_LOW`، فتعرض الواجهة رسالة عامة بدل
سبب الرفض.

## القرار

كل صنف خطأ يحمل علامة بنيوية مقروءة، وحارس نوع يفحص العلامة لا السلسلة:

```ts
export class ServiceError extends Error {
  /** علامة بنيوية: `instanceof` غير موثوق عبر حدود الحزم. */
  readonly isServiceError = true as const
  …
}

export function isServiceError(error: unknown): error is ServiceError {
  return typeof error === 'object' && error !== null
    && (error as ServiceError).isServiceError === true
}
```

والمثل في `TradeError` / `isTradeError`. لا يُستخدم `instanceof` لأي خطأ عابر
لحدود الوحدات.

## بدائل مرفوضة

**فحص `error.name`**: نصّ قابل للتصادم ويضيع مع التصغير في بعض الإعدادات.

**رمز خطأ في `message`**: خلط بين رسالة المستخدم والبيانات الآلية.

**نوع نتيجة `Result<T, E>`**: أنظف نظريًا، لكنه يعيد كتابة كل مسار وكل خدمة،
وهو تغيير أكبر بكثير من المشكلة.

## النتائج

الحارس البنيوي يعمل عبر أي حدود حزم، ويعمل حتى مع خطأ عبر تسلسل بنيوي، ولا
يعتمد على هوية الصنف. الثمن: حقل إضافي في كل صنف خطأ، وقاعدة يجب أن تُحترم —
**لا `instanceof` لأخطاء المجال**.

`ZodError` يُفحص بالطريقتين معًا (`instanceof` **أو** `name === 'ZodError'`)
لأنه من حزمة خارجية قد تُحمَّل مرتين للسبب نفسه.
