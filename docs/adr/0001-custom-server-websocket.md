# ADR-0001: خادم مخصّص يستضيف Next وWebSocket معًا

**الحالة**: مقبول · **يستبدل**: نقل SSE السابق

## السياق

المزايدات بيانات لحظية: مزايدة تصل الآن يجب أن يراها كل مشاهد الآن، لا بعد
دورة استطلاع. المتطلّب صريح: **بيانات لحظية عبر WebSocket أو أفضل المعايير**.

مسارات Next لا تستطيع ترقية الاتصال إلى WebSocket — لا API لذلك في App Router.

## القرار

خادم Node مخصّص واحد ([`server.mjs`](../../server.mjs)) يستضيف معالج طلبات
Next وخادم `ws` في العملية نفسها، ويوجّه ترقيات `/ws` إلى WebSocket وما عداها
إلى معالج ترقيات Next (لإبقاء إعادة التحميل الساخن تعمل).

السجلّ المشترك على `globalThis.__plateRealtime` لأن `server.mjs` وحزمة Next
وحدتان منفصلتان في الذاكرة؛ استيراد الوحدة نفسها من الطرفين يعطي نسختين.

## بدائل مرفوضة

**SSE** (التنفيذ السابق): أحادي الاتجاه، فلا اشتراك بمواضيع ولا حضور مشاهدين
من العميل، ويحتاج اتصالًا لكل صفحة. حدود اتصالات HTTP/1.1 لكل نطاق مشكلة
حقيقية مع عدة تبويبات.

**استطلاع دوري**: تأخير محسوس، وحمل يتناسب مع عدد المشاهدين حتى في السكون.

**خدمة لحظية خارجية** (Pusher / Ably / Supabase Realtime): تحلّ المشكلة لكن
تضيف اعتمادًا خارجيًا وتكلفة ومفتاحًا آخر لإدارته، لتطبيق يعمل الآن على نسخة
واحدة.

## النتائج

**مكاسب**: دفع ثنائي الاتجاه؛ اتصال واحد يخدم عدة مواضيع؛ حضور المشاهدين
مجانًا؛ مكان طبيعي للمسح الدوري الذي ينهي المزادات في وقتها.

**ثمن**: لم يعد `next start` صالحًا — التشغيل عبر `node server.mjs`؛ والنشر
يحتاج بيئة Node طويلة العمر (لا تعمل على منصّات serverless بلا حالة).

**فخّ وقع فعلًا**: `getUpgradeHandler()` قبل `await app.prepare()` يرمي
`prepare() must be called before performing this operation`. الترتيب مقصود
وموثّق في الملف.

## متى يُعاد النظر

عند الحاجة إلى أكثر من نسخة خادم: يبقى القرار، ويُستبدل جسد `publishRealtime`
بناقل مشترك (Redis pub/sub) بلا تغيير في واجهته ولا في كود العميل.
