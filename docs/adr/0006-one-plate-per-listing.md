# ADR-0006: الإعلان = لوحة واحدة، وبنية معلومات مسطّحة

**الحالة**: مقبول · **الدافع**: ملاحظات مستخدم صريحة

## السياق

التصميم الأول ورث بنية البثّ المباشر: **غرفة** تحوي **مزادًا** يحوي **عدّة
لوحات** في طابور، والمضيف ينتقل بينها. ونتج عنه:

- `/rooms` ← `/rooms/{slug}` ← `/auctions` ← `/auctions/{id}` ← اللوحة
- صفحتان مختلفتان لعرض المزاد نفسه: `/bid/{slug}` بمقاس الجوال، وصفحة
  تفاصيل المزاد.

الملاحظة كانت مباشرة: «ليش كل هالتفريعات المبالغ فيها»، و«ما ودي نتشتت وودي
تكون الصفحات موحّدة»، و«المزاد = لوحة واحدة».

## القرار

1. **الإعلان لوحة واحدة**. لا طابور ولا تجميع — ولا حتى في لوحة التحكّم.
2. **السوق مسطّح**: `/market` يعرض كل الإعلانات مباشرة، و`/market/{id}` صفحة
   الإعلان الوحيدة — تفاصيله وكشفه وزرّ التداول فيه.
3. **صفحة واحدة لكل غرض**. حُذفت صفحة المزايدة المنفصلة: الصفحة نفسها متجاوبة
   وتعمل على الجوال، فوجود نسخة «للجوال» تشتيت لا خدمة.

## بدائل مرفوضة

**إبقاء التجميع في لوحة التحكّم فقط**: طُرح، ورُفض صراحةً. نموذجان مختلفان
للبيانات (مجمّع للبائع، مسطّح للمشتري) يعني منطق مزامنة دائمًا بينهما، مقابل
راحة لا يحتاجها البائع.

**مجلّدات أو مجموعات اختيارية**: تعقيد قبل الحاجة.

## النتائج

**مكاسب**: رابط واحد لكل لوحة يُشارك ويُفهرَس؛ الوصول من السوق إلى المزايدة
في نقرة؛ نموذج بيانات أبسط (لا `rooms` ولا `lots` ولا ترتيب طابور ولا «اللوحة
النشطة»)؛ وواجهة واحدة تُصان بدل اثنتين.

**ثمن**: بائع لديه عشرون لوحة ينشر عشرين إعلانًا. مقبول: صفحة «لوحاتي» تعرضها
مجتمعة، والنشر الجماعي يمكن إضافته لاحقًا بلا تغيير النموذج.
