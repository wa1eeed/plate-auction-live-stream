# ADR-0005: الأوامر على HTTP والأحداث على WebSocket

**الحالة**: مقبول

## السياق

بعد اعتماد WebSocket ([ADR-0001](0001-custom-server-websocket.md)) صار السؤال:
هل تُرسَل المزايدة نفسها عبر المقبس؟ فهو مفتوح أصلًا وأقلّ تأخيرًا.

## القرار

**لا.** فصل صريح:

| | الأوامر | الأحداث |
| --- | --- | --- |
| النقل | HTTP `POST`/`PATCH`/`DELETE` | WebSocket |
| تعطي | مصادقة الكوكي، تحديد المعدل، منع التكرار، رمز خطأ، حالة HTTP، إعادة محاولة قياسية | إشعارًا بأن شيئًا تغيّر |

وقاعدة ثانية أهم: **الحدث إشعار لا حالة**. العميل لا يبني حالته من حمولة
الحدث، بل يطلب `GET /api/listings/{id}` عند وصوله.

## لماذا

**الأوامر على HTTP**: المصادقة والمعدل والتحقّق ومنع التكرار كلها موجودة
ومختبَرة على هذا المسار. نقلها إلى المقبس يعني إعادة بناء كل ذلك داخل بروتوكول
رسائل مخصّص — بلا رموز حالة، وبلا إعادة محاولة قياسية، وبلا أدوات فحص.

**الحدث إشعار**: لو بنى العميل حالته من الحمولة لصار هناك مساران لبناء الحالة
(REST والحدث) يجب أن يتّفقا دائمًا. عندها كل حدث ضائع أو مكرّر أو خارج الترتيب
يترك واجهة خاطئة تحتاج تصحيحًا يدويًا. بمسار واحد، أسوأ ما يحدث هو تأخّر
بضع مئات المللي ثانية.

## النتائج

**مكاسب**: مسار واحد لبناء الحالة؛ الفجوة والانقطاع وعودة التبويب كلها تُعالج
بالآلية نفسها — إعادة مزامنة؛ وتعطّل WebSocket نهائيًا لا يكسر الصفحة، بل
يخفض دقّتها الزمنية (سقوط احتياطي إلى جلب دوري كل 8 ثوانٍ).

**ثمن**: طلب REST إضافي بعد كل حدث. عولج بـ:
- **تجميع 200 مللي** — عدة أحداث متتابعة ⇐ طلب واحد. بدونه كان كل مشاهد يُطلق
  طلبًا لكل مزايدة، فيتضاعف الحمل مع عدد المشاهدين.
- **`presence` لا يستدعي مزامنة** — لا يمسّ بيانات الإعلان.
- **الفجوة تُزامن فورًا** لا مجمّعة — نقص مؤكَّد في الحالة.
