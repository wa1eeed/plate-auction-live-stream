# البنية المعمارية

> وثيقة مرجعية لبنية «سوق تداول لوحات المركبات». تشرح العملية، والطبقات،
> ومسار البيانات، ونقاط التوسّع. اقرأها قبل أي تعديل جوهري.

## 1. لمحة سريعة

منصّة ويب عربية (RTL) لتداول لوحات المركبات السعودية. كل مستخدم بائع ومشترٍ
في الوقت نفسه: يعرض لوحاته بثلاث طرق (مزاد / بيع مباشر / استقبال عروض)،
ويتداول على لوحات غيره.

| العنصر | الاختيار |
| --- | --- |
| الإطار | Next.js 15 (App Router) + React 19 |
| اللغة | TypeScript 5.9 في وضع `strict` |
| التنسيق | Tailwind CSS 4 (`@theme` داخل CSS بلا ملف إعداد JS) |
| المكوّنات | Radix UI + طبقة مكوّنات محلية بأسلوب shadcn/ui |
| النماذج | React Hook Form + Zod |
| اللحظية | WebSocket (`ws`) على مسار `/ws` |
| التخزين | واجهة `AuctionStore` — التنفيذ الحالي في الذاكرة |
| الاختبار | Vitest (وحدات) + Playwright (شامل) |

## 2. نموذج العملية

المشروع لا يعمل عبر `next start` بل عبر خادم مخصّص واحد ([`server.mjs`](../server.mjs))
يستضيف Next وخادم WebSocket في **العملية نفسها**.

```
┌──────────────────────── عملية Node واحدة ───────────────────────┐
│                                                                 │
│   node:http server                                              │
│     ├── HTTP  ──────────────▶ Next request handler              │
│     │                          ├── صفحات RSC                    │
│     │                          └── مسارات /api/*                │
│     │                                                           │
│     └── upgrade                                                 │
│           ├── /ws  ─────────▶ WebSocketServer (ws)              │
│           └── غيره ─────────▶ Next upgrade handler (HMR)        │
│                                                                 │
│   globalThis.__plateRealtime   ◀── السجلّ المشترك                │
│   globalThis.__auctionStore    ◀── مثيل التخزين الوحيد           │
│                                                                 │
│   setInterval(HEARTBEAT_MS)  نبضة إسقاط المقابس الميتة           │
│   setInterval(SWEEP_MS)      POST /api/internal/sweep           │
└─────────────────────────────────────────────────────────────────┘
```

### لماذا خادم مخصّص؟

مسارات Next لا تستطيع ترقية الاتصال إلى WebSocket. البدائل (خدمة لحظية
خارجية، أو SSE) إمّا تضيف اعتمادًا خارجيًا أو لا تعطي دفعًا ثنائي الاتجاه
مع حضور المشاهدين. القرار موثّق في [ADR-0001](adr/0001-custom-server-websocket.md).

### السجلّ المشترك على `globalThis`

`server.mjs` وحزمة Next وحدتان منفصلتان في الذاكرة؛ استيراد الوحدة نفسها من
الطرفين يعطي نسختين مختلفتين. لذلك يعيش سجلّ المقابس على `globalThis.__plateRealtime`
ويصل إليه الطرفان: `server.mjs` مباشرةً، وكود التطبيق عبر
[`src/lib/server/realtime.ts`](../src/lib/server/realtime.ts).

المبدأ نفسه ينطبق على `globalThis.__auctionStore` و`globalThis.__rateBuckets`:
هذا أيضًا ما يحفظ الحالة عبر إعادة التحميل الساخن في وضع التطوير.

## 3. الطبقات

```
   الواجهة            src/app/**            صفحات RSC + مكوّنات عميل
      │
      ├── أوامر ─────▶ src/app/api/**       مصادقة، تحقّق Zod، رموز أخطاء
      │                     │
      │                     ▼
      │               src/lib/server/market-service.ts     ← التنسيق
      │                     │
      │                     ├──▶ src/lib/domain/**         ← قواعد نقية
      │                     ├──▶ src/lib/store/**          ← ثبات + ذرّية
      │                     └──▶ src/lib/server/realtime.ts ← نشر الأحداث
      │                                   │
      └── أحداث ◀─────────── /ws ◀────────┘
```

القاعدة الحاكمة: **الاتجاه أحادي**. الطبقة الأدنى لا تعرف شيئًا عن الأعلى.
`src/lib/domain` لا يستورد شيئًا من `server` أو `store` أو React، ولهذا يمكن
اختباره كدوال نقية بلا أي تهيئة.

| المجلد | المسؤولية | ما لا يفعله |
| --- | --- | --- |
| `src/lib/domain` | قواعد التداول والمال والفلاتر والأنواع | لا I/O، لا وقت خارجي (يُمرَّر `nowMs`) |
| `src/lib/store` | التخزين والذرّية ومنع التكرار | لا قواعد عمل |
| `src/lib/server` | التنسيق، الجلسات، التشفير، تحديد المعدل، النشر اللحظي | لا JSX |
| `src/app/api` | حدود HTTP: تحقّق المدخلات وتحويل الأخطاء | لا منطق عمل |
| `src/components` | العرض | لا وصول مباشر للتخزين |

### خدمات الخادم وترتيب اعتمادها

الاتجاه أحادي هنا أيضًا، ولذلك لا حلقات استيراد:

```
market-service          ← المجال والتخزين والنشر اللحظي
   ▲        ▲
   │        └── wallet-service        (المحفظة والعرابين)
   │                 ▲
   │                 └── order-service        (اكتمال الصفقة)
   │                          ▲   │
   │                          │   └──▶ commission-service
   └── admin-service ─────────┘
```

**`order-service` وُجد لسبب**: كان اكتمال الصفقة يقع في مكانين — مسار البائع
في `market-service` ومسار الإدارة في `admin-service` — فحمل الثاني آثاره
المالية ونسيها الأول، فبقيت عرابين المزايدين محجوزة إلى الأبد كلّما أغلق بائع
صفقته بنفسه. جمعُهما في `applyOrderCompletion` يجعل نسيان أثر واحد مستحيلًا.

## 4. فصل الأوامر عن الأحداث (CQRS مبسّط)

| | الأوامر | الأحداث |
| --- | --- | --- |
| النقل | HTTP `POST`/`PATCH`/`DELETE` | WebSocket |
| الاتجاه | عميل ← خادم | خادم ← عميل |
| تعطي | مصادقة، تحديد معدل، منع تكرار، رمز خطأ دقيق، حالة HTTP | إشعارًا بأن شيئًا تغيّر |
| الحمولة | كاملة ومتحقَّق منها | **إشعار فقط**، لا حالة موثوقة |

الحدث اللحظي ليس مصدر الحقيقة: يصل الحدث فيطلب العميل مزامنة كاملة عبر
`GET /api/listings/{id}`. بهذا لا يوجد مسار ثانٍ لبناء الحالة، وأي فجوة أو
انقطاع تُصحَّح تلقائيًا. التفاصيل في [بروتوكول اللحظية](realtime-protocol.md)
و[ADR-0005](adr/0005-commands-http-events-websocket.md).

## 5. مسار مزايدة كاملة

```
المزايد                الخادم                        بقية المشاهدين
  │                       │                                 │
  ├── POST /listings/{id}/bids                              │
  │      { amount, isCustomAmount, clientRequestId }        │
  │                       │                                 │
  │            requireUserId()            المصادقة          │
  │            placeBidSchema.parse()     تحقّق الشكل        │
  │            rateLimit(bid:user:listing) 6/10ث            │
  │                       │                                 │
  │            mutex.run('listing:{id}')  ← تسلسل ذرّي       │
  │              ├─ dedupe(clientRequestId)                 │
  │              ├─ assertBidIsValid()   ← قواعد نقية       │
  │              ├─ حفظ المزايدة + serverSequence           │
  │              └─ computeExtension()   ← تمديد تلقائي     │
  │                       │                                 │
  │            publish('bid_placed')                        │
  │              ├─ appendEvent (سجلّ دائم)                 │
  │              └─ publishRealtime([listing:{id}, market]) │
  │                       │                                 │
  │◀── 200 { bidId, amount, endsAt, extended }              │
  │                       ├──── ev bid_placed seq=n ───────▶│
  │                       │                                 │
  │                       │◀─── GET /api/listings/{id} ─────┤ مزامنة
  │                       │──── ListingDetail ─────────────▶│
```

النقطة الحرجة: **لا يُوثق بأي قيمة من العميل**. المبلغ المطلوب يُحسب على
الخادم من حالة الإعلان، والوقت من ساعة الخادم، والهوية من كوكي موقّع.

## 6. الذرّية ومنع التكرار

عمليتان حرجتان: `placeBid` و`buyNow`. كلتاهما تُنفَّذان داخل
[`KeyedMutex`](../src/lib/store/mutex.ts) بمفتاح `listing:{id}`، فيتسلسل
المتزامنون على الإعلان الواحد بينما تبقى الإعلانات الأخرى متوازية.

منع التكرار: كل أمر يحمل `clientRequestId`؛ يُحفظ في `db.requestIds` ويُعاد
الناتج نفسه عند تكرار الطلب، فلا تُسجَّل مزايدة مرّتين عند إعادة المحاولة
الشبكية أو النقر المزدوج.

عند الانتقال إلى PostgreSQL تنتقل هذه الضمانة إلى الدالة المخزّنة
(`SELECT ... FOR UPDATE` أو `place_bid()`) — انظر [ADR-0003](adr/0003-store-abstraction.md).

## 7. إنهاء المزادات في وقتها

المزاد يجب أن ينتهي في وقته حتى لو لم يفتح أحد أي صفحة. لذلك:

1. `server.mjs` يستدعي `POST /api/internal/sweep` كل `SWEEP_MS` (5 ثوانٍ).
2. المسار محمي بترويسة `x-internal-sweep` تساوي `SESSION_SECRET`.
3. `finalizeDueAuctions()` ينقل المجدول إلى نشط، وينهي المستحق، وينشئ الطلب
   للفائز، وينشر `auction_ended`.

الاستدعاء يمرّ عبر HTTP لا باستدعاء الدالة مباشرة، لأن حزمة Next تملك نسختها
الخاصة من الوحدات (المشكلة نفسها في القسم 2).

`finalizeDueAuctions` تُستدعى أيضًا عند كل قراءة للسوق أو للإعلان، فتبقى
النتيجة صحيحة حتى لو تعطّل المسح الدوري.

**والمبدأ نفسه في تذكيرات مهلة السداد**: `sendPaymentReminders` تعمل على مسارات
القراءة (صفحة المشتريات، صفحات الإدارة) لا في مؤقّت خلفي. مؤقّتٌ في الذاكرة لا
ينجو من إعادة تشغيل ولا من تعدّد النسخ؛ والمسح عند القراءة يجعل الحالة صحيحة
لحظة يحتاجها من ينظر إليها، وهو الوقت الوحيد الذي يهمّ.

## 8. الحالة في العميل

| الحالة | المكان |
| --- | --- |
| بيانات الإعلان | `useListing` — جلب REST + مزامنة عند الأحداث |
| الاتصال اللحظي | `useRealtime` — حالة الاتصال وعدد المشاهدين |
| العدّاد | `useCountdown` — يُهيّأ من `endsAt` و`serverTime` القادمين من الخادم |
| الفلاتر | حالة محلية في `market-grid` فوق منطق نقي في `market-filters.ts` |

العدّاد يُهيّأ من قيمة الخادم لا من `Date.now()` في التصيير الأولي، وإلا اختلف
ناتج الخادم عن العميل وحدث عدم تطابق في الترطيب (hydration).

## 9. حدود النظام الحالية

مقصودة وموثّقة، لا مفاجآت:

- **التخزين في الذاكرة**: تُفقد البيانات عند إعادة التشغيل، ولا يعمل على أكثر
  من نسخة خادم. الواجهة `AuctionStore` مجرّدة بالكامل استعدادًا لـ PostgreSQL.
- **البثّ اللحظي داخل العملية**: مع أكثر من نسخة يحتاج ناقلًا مشتركًا (Redis
  pub/sub أو ما يعادله) بين النسخ.
- **تحديد المعدل في الذاكرة**: للنسخة الواحدة.
- **لا سداد داخل المنصّة**: الطلب توثيق للصفقة، والسداد ونقل الملكية خارجها.
  ولذلك تُقتطع عمولة المنصّة من **المحفظة** لا من ثمن اللوحة.
- **تذكيرات المهلة على القراءة**: من لا يفتح صفحة ولا تُفتح صفحة إدارية لا
  يصله تذكيره في لحظته بالضبط. مقبول ما دامت الإدارة تفتح لوحتها يوميًا؛ ومع
  قاعدة بيانات حقيقية يصير المسح مهمّة مجدولة.
