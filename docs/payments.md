# المدفوعات

> شحن رصيد المحفظة: بوابة Tap للبطاقات، والحوالة البنكية بتحقّق إداري.
> المصادر: [`tap-client.ts`](../src/lib/server/tap-client.ts) ·
> [`payment-service.ts`](../src/lib/server/payment-service.ts)

## 1. أين يدخل المال

المحفظة هي المدخل الوحيد للمال إلى المنصّة، وشحنها بطريقتين يضبطهما الأدمن:

| الطريقة | المسار | متى يُضاف الرصيد |
| --- | --- | --- |
| **بطاقة عبر Tap** | صفحة دفع مستضافة لدى Tap | فور تأكيد البوابة (ويبهوك أو مزامنة) |
| **حوالة بنكية** | بيانات الحساب تظهر للمستخدم | بعد تحقّق الأدمن من وصولها |

ويمرّ بالطريقين شيئان: **شحن رصيد المحفظة** الذي تُحجز منه العرابين،
و**سداد صفقة** بعينها — يفرّق بينهما `Payment.orderId`. وسداد الصفقة لا يشحن
محفظة: يُحجز أمانةً حتى تُنقل الملكية. وثالثةُ الطرق **الرصيد نفسه**: من في
محفظته ما يكفي يُتمّ سداده بلا بوابة.

## 2. المفاتيح السرّية — أين تعيش

**في متغيّرات البيئة وحدها.**

```bash
TAP_TEST_SECRET_KEY=sk_test_…
TAP_LIVE_SECRET_KEY=sk_live_…
```

لا تُخزَّن في قاعدة البيانات، ولا تُرسل إلى العميل، ولا تظهر في أي واجهة، ولا
تُسجَّل في أي مخرج. مفتاح في قاعدة البيانات يعني تسريبه مع أي نسخة احتياطية أو
استعلام أو تفريغ للتصحيح.

**الأدمن يختار البيئة لا المفتاح.** لوحة الإعدادات تعرض *حالة تهيئة* كل بيئة
(«المفتاح مضبوط» / «بلا مفتاح») ولا تعرض قيمته ولا تقبل إدخاله.

ولا يمكن تفعيل بيئة بلا مفتاح: الخادم يرفض بـ `409 TAP_NOT_CONFIGURED`، وواجهة
المستخدم لا تعرض الخيار أصلًا. زرّ دفع يفشل حتمًا أسوأ من غيابه.

## 3. البيئة التجريبية والحقيقية

| | تجريبية | حقيقية |
| --- | --- | --- |
| المفتاح | `TAP_TEST_SECRET_KEY` | `TAP_LIVE_SECRET_KEY` |
| البطاقات | بطاقات اختبار Tap | بطاقات فعلية |
| الخصم | لا يقع | يقع فعلًا |
| ما يراه المستخدم | شارة «وضع تجريبي» على خيار البطاقة | لا شارة |

التبديل من لوحة الإدارة فوريًا، ومع تفعيل البيئة الحقيقية يظهر للأدمن تحذير
صريح بأن كل عملية تخصم مالًا فعليًا.

## 4. مسار الدفع بالبطاقة

```
المستخدم                    منصّتنا                        Tap
   │                           │                            │
   ├── شحن 1000 ريال ─────────▶│                            │
   │                  إنشاء Payment(initiated)              │
   │                           ├── POST /v2/charges ───────▶│
   │                           │◀── { id, transaction.url }─┤
   │◀── تحويل إلى صفحة Tap ─────┤                            │
   │                           │                            │
   ├────────────── يدفع على صفحة Tap ─────────────────────▶ │
   │                           │◀── ويبهوك (hashstring) ────┤
   │                           │   تحقّق التوقيع             │
   │                           ├── GET /v2/charges/{id} ───▶│
   │                           │◀── الحالة الحقيقية ────────┤
   │                           │   CAPTURED ⇒ قيد topup     │
   │◀── العودة إلى /account/wallet/return                   │
   │            (تُعيد المزامنة أيضًا — احتياطًا)             │
```

**بيانات البطاقة لا تمرّ بخوادمنا إطلاقًا.** نستعمل `source.id = 'src_all'`
فتفتح صفحة Tap المستضافة بكل وسائل الدفع المفعّلة للتاجر.

**لا نصدّق العودة إلى صفحة النجاح.** من يفتح `/account/wallet/return` يدويًا لا
يشحن رصيده: نقرأ حالة العملية من البوابة مباشرة، والبوابة وحدها مصدر الحقيقة.

## 5. الويبهوك وتوقيعه

`POST /api/webhooks/tap`

Tap يرسل ترويسة `hashstring` = HMAC-SHA256 بالمفتاح السرّي على الحقول
بهذا الترتيب بالضبط:

```
x_id{id}x_amount{amount}x_currency{currency}
x_gateway_reference{ref}x_payment_reference{ref}x_status{status}x_created{created}
```

المبلغ بعدد خانات عملته العشرية (الريال بخانتين). والمقارنة **ثابتة الزمن**
(`timingSafeEqual`) — مقارنة نصية عادية تسرّب التوقيع حرفًا حرفًا.

**بلا هذا التحقّق يستطيع أي طرف إرسال «تم الدفع» فيشحن رصيده مجانًا.**
التوقيع الفاشل يعيد `401` لا `200`: نريد أن يظهر الرفض في سجلّات Tap لا أن
يُبتلع بصمت.

وبعد التحقّق **لا نصدّق حالة الحمولة** أيضًا — نقرأ العملية من البوابة، فالحمولة
قد تكون قديمة أو ناقصة.

## 6. مسار الحوالة البنكية

```
المستخدم يطلب شحنًا  ⇒  awaiting_transfer  ← تظهر بيانات الحساب + مرجع TOP-XXXXXX
        │
        ├── يحوّل خارج المنصّة ويكتب المرجع في الملاحظات
        │
        └── يبلّغ برقم عمليته  ⇒  under_review
                    │
        ┌───────────┴───────────┐
   الأدمن يؤكّد            الأدمن يرفض
        │                      │
      paid                  failed
  + قيد topup           + سبب يظهر للمستخدم
```

**المرجع `TOP-XXXXXX`** هو ما يربط الحوالة بصاحبها: يكتبه المستخدم في خانة
ملاحظات التحويل، ويبحث به الأدمن في كشف حساب المنصّة. وبيانات الحساب تُعرض مع
**زرّ نسخ لكل حقل** — نسخ الآيبان يدويًا من الشاشة مصدر أخطاء شائع.

ولا يظهر خيار الحوالة بلا آيبان مضبوط: لا نعرض حسابًا ناقصًا يُحوَّل إليه.

## 7. منع الشحن المزدوج

الضمانة الأهمّ في هذا الملف كلّه.

كل عملية دفع تحمل `ledgerEntryId`. وجوده يعني أن الرصيد أُضيف، فـ`markPaymentPaid`
تعود فورًا بلا أثر جديد. هذا يحمي من:

- ويبهوك يصل مرّتين (Tap يعيد المحاولة عند أي خطأ)
- المستخدم يحدّث صفحة العودة مرارًا
- الأدمن يضغط «تأكيد» مرّتين
- تزامن ويبهوك مع عودة المستخدم في اللحظة نفسها

ويحرسه اختبار صريح: ثلاث محاولات تأكيد متتالية تنتج قيد شحن **واحدًا**.

كذلك لا تُرفض عملية أُضيف رصيدها (`409 PAYMENT_SETTLED`) — الرفض بعد الإضافة
يترك رصيدًا بلا مقابل.

## 8. حالات العملية

| الحالة | المعنى |
| --- | --- |
| `initiated` | أُنشئت وبانتظار توجّه المستخدم لصفحة Tap |
| `awaiting_transfer` | حوالة: عُرضت البيانات وننتظر التحويل |
| `under_review` | أبلغ المستخدم بالتحويل وننتظر تحقّق الإدارة |
| `paid` | تأكّد الدفع وأُضيف الرصيد |
| `failed` | رُفض أو فشل — مع سبب يظهر للمستخدم |
| `cancelled` | ألغاها المستخدم قبل الدفع |

## 8.5 سداد الصفقات — صفحة موحّدة

شحن الرصيد شيء وسداد صفقة شيء آخر: الأول يُدخل مالًا إلى محفظة، والثاني يُغلق
بيعًا. لذلك `Payment.orderId` — `null` لشحن، ومُعبّأ لسداد صفقة بعينها. بدونه لا
يُعرف عمّاذا دُفع.

### المسار

```
شراء مباشر  ──┐
              ├──► /checkout/{orderId}  ──►  /checkout/{orderId}/thanks
مزاد رسا    ──┘        بريك داون                 إيصال + «عرض الطلب»
                    + وسيلة الدفع
```

الشراء المباشر **يُسجّل الصفقة أولًا** ثم ينقل إلى السداد: فتُحجز اللوحة ولا
يسبقه غيره أثناء مراجعته للتفاصيل. والفائز بمزاد يصل إليها من «مشترياتي» بزرّ
**أكمل السداد**.

### البريك داون

```
قيمة الصفقة                          35,000.00
العربون المحجوز (يُخصم عند الإتمام)  −  4,000.00
عمولة المنصّة                        +    875.00
ضريبة القيمة المضافة (على العمولة)   +    131.25
────────────────────────────────────────────────
المطلوب سداده                          32,006.25
```

**العمولة داخل المجموع لا بجانبه.** كانت تُعرض ولا تُحتسب، فيرى المشتري رقمًا
أقلّ ممّا سيدفع — وهو أسوأ ما يقع في شاشة دفع.

### الوسائل الثلاث

| الوسيلة | ما تفعله | متى تُعطَّل |
| --- | --- | --- |
| رصيد المحفظة | يُخصم فورًا و**تكتمل الصفقة** في العملية نفسها | المتاح أقلّ من المطلوب |
| بطاقة عبر Tap | تحويل إلى صفحة البوابة ثم العودة | البوابة معطّلة في الإعدادات |
| حوالة بنكية | تُعرض بيانات الحساب، وتُعتمد بتحقّق الإدارة | الحوالة معطّلة في الإعدادات |

**المعطّلة تُعرض ولا تُخفى**، ومعها سبب تعطيلها: من لا يجد وسيلته يظنّها غير
مدعومة، ومن يراها معطّلة بسبب مذكور يعرف ما يفعل.

### شوكة واحدة: شحن محفظة أو تسوية صفقة

`markPaymentPaid` تتفرّع على `payment.orderId` ولا تفعل الاثنين أبدًا:

| `orderId` | ما يقع |
| --- | --- |
| `null` | قيد `topup` في محفظة صاحبها — كما كان |
| مملوء | `settleOrderPayment`: تُتمّ الصفقة ولا تُضيف رصيدًا |

كانت الدالّة تعرف فعلًا واحدًا — كتابة `topup` — فتطبّقه على كل عملية. فمن حوّل
ثمن لوحة بحوالة بنكية يجد المبلغ **رصيدًا في محفظته** وتبقى صفقته «بانتظار
السداد» إلى الأبد.

### الدفعة الخارجية: قيد محفظة واحد لا غير

في البطاقة والحوالة **المال يصل حساب المنصّة أو بوابتها، لا محفظة المشتري**.
فلا يُخصم من محفظته ثمن اللوحة (لم يدخلها) ولا العمولة (دفعها ضمن المبلغ
الخارجي). القيد الوحيد هو **خصم العربون** — المال الوحيد الذي كان فيها فعلًا.

```
حوالة بنكية لصفقة قيمتها 35,000 وعربونها 4,000 وعمولتها 875 + 131.25 ضريبة:

المحفظة:        deposit_applied  −4,000        ← القيد الوحيد
إيراد المنصّة:  commission_buyer  875   محصَّل  ← ledgerEntryId = null
                vat_buyer         131.25 محصَّل     paymentId = P26-00001
```

قيد الإيراد يحمل `paymentId` ويترك `ledgerEntryId` فارغًا: اجتماعهما هكذا يعني
**حُصّل خارج المحفظة** لا تناقضًا.

### التفصيل مجمَّد لا مُعاد حسابه

`Payment` يحمل `orderPrice` و`buyerCommission` و`buyerVat` مجمّدة لحظة الإنشاء.
بين بدء الحوالة وتأكيدها قد تُغيَّر نسبة العمولة أو تُعطَّل، فالإيراد يُقيَّد
بما دفعه المشتري فعلًا لا بما تقوله الإعدادات لحظة التأكيد.

### حالات لا تُسوَّى

| الحالة | ما يقع |
| --- | --- |
| الدافع ليس مشتري الصفقة | `under_review` بسبب مذكور — **بلا أي قيد** |
| الصفقة ملغاة أو مكتملة أو متخلّفة | `under_review` — المال وصل فعلًا، فإسقاطه صمتًا يضيّعه |
| تأكيد مكرّر | `settledAt` يختم التسوية فلا تتكرّر |

وختم التسوية `settledAt` لا `ledgerEntryId`: صفقة **بلا عربون وبعمولة معطّلة**
تُسوَّى بصفر قيود محفظة، فحارس القيد وحده يسمح بإعادة تسويتها.

### الخصم مرّة واحدة لا مرّتين

الدفع من المحفظة يخصم **ثمن اللوحة بعد العربون فقط**، ثم يُغلق الصفقة بالمسار
المعتاد (`applyOrderCompletion`) فيُخصم العربون وتُقتطع العمولة وضريبتها وتُفكّ
عرابين الباقين.

ولو خُصم «المطلوب» كاملًا هنا لخُصمت العمولة مرّتين: مرّة ضمنه ومرّة في
`chargeOrderCommission`. وقع ذلك فعلًا فخرج من المحفظة **37,012.50** بدل
**32,006.25** — والفرق أن المعروض يجمع الأسطر، والدفتر يفصلها سطرًا سطرًا.

الخارج من المحفظة إجمالًا = **ثمن اللوحة + العمولة + الضريبة**؛ العربون جزء من
الثمن لا زيادة عليه.

### صفحة الشكر

تفرّق بين **سُدّد** و**بدأ السداد**: المحفظة تُتمّ فورًا، والبطاقة والحوالة
تنتظران ردّ البوابة أو تحقّق الإدارة. وإخبار المشتري بأن صفقته تمّت وهي معلّقة
يجعله يظنّ اللوحة ملكه. وفيها رقم العملية، والبريك داون، ومسار الصفقة، وزرّ
**عرض الطلب**.

## 9. الواجهة البرمجية

| المسار | الوظيفة |
| --- | --- |
| `GET /api/payments` | خيارات الدفع المفعّلة + عمليات المستخدم |
| `POST /api/payments` | بدء شحن — يعيد `redirectUrl` لـ Tap أو بيانات الحوالة |
| `GET /api/payments/{id}` | مزامنة الحالة مع البوابة |
| `POST /api/payments/{id}` | إرفاق رقم الحوالة |
| `DELETE /api/payments/{id}` | إلغاء عملية لم تُدفع |
| `POST /api/webhooks/tap` | ويبهوك Tap — توقيع إلزامي |
| `POST /api/admin/payments/{id}` | `{ decision: 'confirm' \| 'reject', reason }` |
| `GET PATCH /api/admin/settings/payments` | قراءة وتعديل الإعدادات |

الحدود: أقل شحن **50 ريالًا**، وأقصاه **500,000**، وبمعدّل **5 عمليات/دقيقة**
لكل مستخدم.

## 10. قائمة فحص التفعيل الحقيقي

- [ ] `TAP_LIVE_SECRET_KEY` مضبوط في بيئة الإنتاج (لا في المستودع)
- [ ] `NEXT_PUBLIC_APP_URL` يشير إلى النطاق العام الحقيقي
- [ ] عنوان الويبهوك في لوحة Tap = `https://<النطاق>/api/webhooks/tap`
- [ ] الويبهوك يصل من الإنترنت (لا محجوب خلف جدار)
- [ ] جُرّبت عملية كاملة في البيئة التجريبية أولًا
- [ ] البيئة الحقيقية فُعّلت من لوحة الإدارة بعد نجاح التجربة
